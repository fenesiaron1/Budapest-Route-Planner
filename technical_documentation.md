# Technical Documentation – Budapest Route Planner
 
## Project Goal
 
This project is a route planner for getting around Budapest. The user picks a start and an end point on a map, chooses how they want to travel (walking, public transport, or driving) and the app shows a route between the two points along with the distance and how long it will take. Driving routes also show live traffic. The app remembers a few personal locations (like home or work) and a light/dark theme, and it also shows nearby BKK public transport stations with basic information about each one.
 
## How the OpenLayers Map Works
 
The map is built with a library called OpenLayers, which draws an interactive map inside the page using tiles (small map images) from an online map provider. On top of the base map, the app uses several separate layers, one for each type of thing shown on the map: the user's route markers, the drawn route itself, the user's current location, saved locations, and BKK stations. Keeping these as separate layers makes it easy to control what's shown on top of what, and to update one type of marker without touching the others. Each marker is a point with a small icon or color attached to it, and routes are drawn as lines. Clicks, hovering, and right-clicks on the map are all handled through OpenLayers' built-in event system, which is how the app knows when the user picked a point, hovered over a marker, or right-clicked a station.
 
## How Route Calculation Works
 
The app can get directions from different services depending on how the user wants to travel. Walking and public transport routes both come from BKK's own routing API, since it can plan both types of trips through the same request, only one setting (which travel modes to allow) needs to change between them. Driving routes come from TomTom's routing service, which also includes live traffic information. When the user doesn't pick a travel mode themselves, the app quietly checks how far apart the two points are first, and then automatically picks walking, public transport, or driving based on that distance, so short trips don't accidentally get turned into a driving route. Since each of these services sends back its results in a different format, the app converts every result into one common, simple format before showing it, so the rest of the app doesn't need to know or care which service actually calculated the route.
 
## How Routing Appears on the Map
 
Once a route comes back from one of the services, it's drawn as a line (or several lines) on the map, replacing whatever route was shown before. Public transport routes are drawn piece by piece: each part of the trip (a walk to the stop, a tram ride, another walk, etc.) is drawn separately, with public transport legs colored using BKK's own colors for that line, and walking legs shown as a dashed line so it's clear they're not a ride. Driving routes are drawn as one solid line first, and then any parts of the route affected by traffic are drawn again on top in a different color depending on how bad the delay is. Alongside the line on the map, the same route result also fills in the distance, travel time, and a short recommendation text in a small info panel.
 
## Methods Used for Mobile Appearance
 
Mobile support was handled almost entirely with CSS, without writing separate code for phones. The page has the standard mobile viewport setting so it scales correctly on small screens. The floating buttons and info panels are sized using percentages and maximum widths instead of fixed pixel sizes, so they shrink to fit narrow screens instead of overflowing. Below a certain screen width, the text and buttons get slightly bigger, since tapping with a finger is less precise than clicking with a mouse. The side panel for saved places also gets wider on small screens and can scroll internally if it has more content than fits on the screen at once. Touch gestures like pinching to zoom and dragging to pan already work out of the box, since OpenLayers supports them by default, so no extra code was needed for that part.
 
## Problems Encountered
 
A few specific bugs came up while building the routing features. The first was caused by how the routing functions were called: the main routing function called each specific routing function (walking, transit, driving) without using `await` in front of it. This meant the error-handling code wrapped around that call never actually caught anything, since the outer function had already finished before the inner one could fail, so instead of showing a friendly error message, a failed request caused an "unhandled promise rejection" error in the console. This was fixed by adding `await` in front of each call, so the outer error handling actually works as intended. The second issue was that BKK's routing API doesn't support planning a pure cycling route the way the previous routing service did, so cycling had to be dropped as a travel option once walking and public transport were switched over to BKK. The third issue came from misreading BKK's response format: the first version of the code tried to read the trip details directly from the top level of the response, but the actual data was nested one level deeper, inside an extra field, this caused the app to crash with an error about reading a property of "undefined" until the correct, deeper path was used. The fourth issue was a console warning caused by calling `getFeaturesAtPixel`, which the app uses to detect whether the mouse is hovering over a clickable marker; since this function is called on every single mouse movement over the map, calling it this frequently triggered a warning, even though it didn't break anything visible to the user.

## Possible Future Improvements
 
There are still a few limitations worth improving. Routing depends on the free public OSRM server, which isn't guaranteed to stay online and can slow down or stop responding under heavy use. The free TomTom plan only allows a limited number of requests per day, so driving routes will stop working once that daily limit is used up. Traffic sections often come back marked as either "no delay" or "unknown," since TomTom can only report a real delay level where it actually has live traffic data for that road. Public transport routes only show the path taken, without labeling which specific bus, tram, or metro line to take. The app only supports planning a trip between two points, with no way to add extra stops along the way. Saved locations and the light/dark theme are stored in the browser itself, so they don't carry over to a different browser or device. Finally, the app needs the user to allow location access before it can show their current position on the map.
